# ADR 0014 — Refunds and reconciliation (Sprint 5c)

**Status:** Accepted

| Decision                                                                                                                                                                                                                                                                                                                                    | Rationale                                                            | Alternative considered                 |
| ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------- | -------------------------------------- |
| Refunds are scheduled per deposit (reason, due date; unsuccessful bidders default to N business days, setting) and paid in **batches**: one finance user prepares (`refunds.issue`), a **different** user approves (`refunds.approve`), enforced on the server (P5)                                                                         | Four eyes on every rand that leaves                                  | Single approver                        |
| The refund amount is always the deposit's **ledger balance** when the batch is prepared (includes over-payments)                                                                                                                                                                                                                            | No manual amounts                                                    | Typed amounts                          |
| EFT refunds only to the bidder's **verified and locked** account; otherwise the refund is held back with the reason shown                                                                                                                                                                                                                   | Refunds cannot be redirected                                         | Warn only                              |
| Escrowed deposits are refunded by their provider on approval (TradeSafe `transactionCancel` must return `REFUNDED`; Paystack refund API); a failed provider refund leaves the batch (total adjusted, noted) and returns to "scheduled" for the next batch; a batch whose refunds all failed is **cancelled**, not "paid" (found in testing) | Honest batch status; automatic retry                                 | Leave failed refunds in a "paid" batch |
| EFT refunds: after approval finance downloads a payment file (generic CSV; adapt to the bank's import format), pays at the bank, and uploads the bank's confirmation; only then are refunds recorded as paid                                                                                                                                | Proof for every payment                                              | Mark paid on approval                  |
| Paying a refund adds a negative ledger entry, issues a numbered refund receipt and emails it; the refund account **unlocks only when no other deposit of that bidder is held**                                                                                                                                                              | Account lock covers every open deposit                               | Unlock per deposit                     |
| Reconciliation recomputes from the ledger and checks: each deposit's status against its balance, bank-statement money against bank ledger entries, paid refunds against refund ledger entries; "Balanced to the cent" only when all agree; full ledger CSV export for the accountant                                                        | Differences are found, not hidden                                    | Totals only                            |
| Dates are immutable in this app (`CarbonImmutable`): date arithmetic must be reassigned (`$d = $d->addDay()`); the business-day loop would otherwise never advance (found in testing; no other occurrences in the codebase)                                                                                                                 | Correct, terminating date maths                                      | —                                      |
| Business days skip weekends but not public holidays yet                                                                                                                                                                                                                                                                                     | Known gap: add a South African public-holiday calendar before launch | —                                      |
