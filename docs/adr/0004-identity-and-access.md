# ADR 0004 — Identity and access (Sprint 2b)

**Status:** Accepted

| Decision                                                                                                                                         | Rationale                                                                                                                                                           | Alternative considered                             |
| ------------------------------------------------------------------------------------------------------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------- |
| Users keep an internal numeric `id`; every user also has a public `ulid` used in URLs and props. The numeric id is hidden from the browser.      | Fortify, passkeys, sessions and spatie/permission all key on numeric ids; a ULID primary key would need changes in each. Public ULIDs still prevent id enumeration. | ULID primary key (spec 5.1 wording)                |
| One `users` table with a `type` of staff, buyer or seller                                                                                        | One login system, one password reset, one 2FA implementation                                                                                                        | Separate staff and buyer tables and guards         |
| Staff join only by emailed invitation (72 h, single use, SHA-256 hash stored, row-locked on accept)                                              | No public route can create a staff account                                                                                                                          | Admin sets a password for new staff                |
| Staff must confirm 2FA before any back-office page (`staff.2fa` middleware)                                                                      | Spec 5.2; back-office accounts control money and personal data                                                                                                      | Optional 2FA with reminders                        |
| Deactivation, never deletion; sessions deleted at once and every request re-checks active status; at least one active super admin always remains | Audit trail and KYC retention; immediate lock-out                                                                                                                   | Soft delete                                        |
| Self-service account deletion removed                                                                                                            | Bidder, deposit and KYC records must be kept by law                                                                                                                 | Keep starter-kit "delete account"                  |
| System role permissions come from `PermissionCatalogue` and are re-synced on every deploy; admins create custom roles for other mixes            | Predictable defaults; deploys can add permissions safely                                                                                                            | Editable system roles (risk of drift and lock-out) |
| Super admin passes all checks via `Gate::before`; deactivated users fail all checks                                                              | Single, testable rule                                                                                                                                               | Grant every permission only                        |
| Database session driver (encrypted) instead of Redis                                                                                             | Needed to list signed-in devices and revoke them per user                                                                                                           | Redis sessions without a device list               |
| Argon2id password hashing in production (`HASH_DRIVER`)                                                                                          | Spec 5.2; memory-hard. Existing hashes upgrade on next login                                                                                                        | bcrypt                                             |
| Staff lifecycle raises domain events (`StaffInvited`, `StaffDeactivated`, `StaffRoleChanged`…)                                                   | Sprint 2c's audit log subscribes without changing these actions                                                                                                     | Write audit rows inside each action                |
| `/dashboard` redirects by account type (staff → `/admin`, buyer → `/account`)                                                                    | One Fortify "home" for login, sign-up and verification                                                                                                              | Custom Fortify response classes                    |
