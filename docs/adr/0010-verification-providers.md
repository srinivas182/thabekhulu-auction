# ADR 0010 — Verification providers (Sprint 4a)

**Status:** Accepted (4a-1 framework; 4a-2 adds the buyer journey)

| Decision                                                                                                                                                                                                                                                                                        | Rationale                                                                                          | Alternative considered |
| ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------- | ---------------------- |
| Three built-in adapters behind one `VerificationProvider` interface: Smile ID (primary, SA), VerifyID (SA alternative), Sumsub (passports, foreign investors); "manual review" always available (K1)                                                                                            | Thabekhulu chooses providers by contract and price; switching is a routing change, not development | Hard-wire one provider |
| Super admin enables providers, enters keys and routes each check type (SA ID, passport, liveness, company, screening, bank account); only enabled, **ready** providers that support a check can be routed; if a routed provider is later disabled, checks fall back to manual review            | Safe configuration without a developer                                                             | Config files           |
| Credentials stored with Laravel's `encrypted:array` cast; secrets write-only (UI shows the last 4 characters; blank keeps the saved value) (K2)                                                                                                                                                 | Keys never reach the browser or logs                                                               | Keys in `.env`         |
| Signing per provider documentation: Smile ID = base64 HMAC-SHA256(api_key, timestamp + partner_id + "sid_request"), also used to verify callbacks; Sumsub = hex HMAC-SHA256(secret, ts + METHOD + path?query + body) with `X-App-*` headers; Sumsub webhooks checked against `X-Payload-Digest` | Matches the providers' published schemes; tests assert the exact signatures                        | —                      |
| VerifyID's authentication is shared with registered clients only, so its adapter is marked **not ready** and cannot be enabled or routed until completed against sandbox credentials                                                                                                            | No integration that only looks finished                                                            | Guess the API          |
| Results normalised to passed / review / failed; Smile ID decided on its explicit `Verify_ID_Number` and `Names` actions; anything unclear, unavailable or partially matched goes to review (K4)                                                                                                 | Never auto-pass a doubtful result                                                                  | Map result codes only  |
| Webhooks: CSRF-exempt path `/webhooks/*`, signature required, throttled, and each provider event stored once (unique provider + event id) (K5)                                                                                                                                                  | Forged callbacks rejected; retries harmless                                                        | Polling                |
| Only references, outcomes and short reasons stored; raw provider responses are not (K3)                                                                                                                                                                                                         | POPIA data minimisation                                                                            | Store full responses   |
| SA ID numbers validated locally (date of birth + Luhn check digit) before any paid check; stored encrypted with a keyed hash for one-account-per-ID                                                                                                                                             | Saves failed paid lookups; no plain-text ID numbers                                                | Plain storage          |
