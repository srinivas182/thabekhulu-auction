# ADR 0010 — Verification providers (Sprint 4a)

**Status:** Accepted (4a-1 framework; 4a-2 adds the buyer journey)

| Decision                                                                                                                                                                                                                                                                                        | Rationale                                                                                          | Alternative considered |
| ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------- | ---------------------- |
| Three built-in adapters behind one `VerificationProvider` interface: Smile ID (primary, SA), VerifyID (SA alternative), Sumsub (passports, foreign investors); "manual review" always available (K1)                                                                                            | Thabekhulu chooses providers by contract and price; switching is a routing change, not development | Hard-wire one provider |
| Super admin enables providers, enters keys and routes each check type (SA ID, passport, liveness, company, screening, bank account); only enabled, **ready** providers that support a check can be routed; if a routed provider is later disabled, checks fall back to manual review            | Safe configuration without a developer                                                             | Config files           |
| Credentials stored with Laravel's `encrypted:array` cast; secrets write-only (UI shows the last 4 characters; blank keeps the saved value) (K2)                                                                                                                                                 | Keys never reach the browser or logs                                                               | Keys in `.env`         |
| Signing per provider documentation: Smile ID = base64 HMAC-SHA256(api_key, timestamp + partner_id + "sid_request"), also used to verify callbacks; Sumsub = hex HMAC-SHA256(secret, ts + METHOD + path?query + body) with `X-App-*` headers; Sumsub webhooks checked against `X-Payload-Digest` | Matches the providers' published schemes; tests assert the exact signatures                        | —                      |
| VerifyID's authentication is shared with registered clients only, so its adapter is marked **not ready** and cannot be enabled or routed until completed against sandbox credentials                                                                                                            | No integration that only looks finished                                                            | Guess the API          |
| Results normalised to passed / review / failed; Smile ID decided on its explicit `Verify_ID_Number` and `Names` actions; anything unclear, unavailable or partially matched goes to review (K4)                                                                                                 | Never auto-pass a doubtful result                                                                  | Map result codes only  |
| Webhooks: CSRF-exempt path `/webhooks/*`, signature required, throttled, and each provider event stored once (unique provider + event id) (K5)                                                                                                                                                  | Forged callbacks rejected; retries harmless                                                        | Polling                |
| Only references, outcomes and short reasons stored; raw provider responses are not (K3)                                                                                                                                                                                                         | POPIA data minimisation                                                                            | Store full responses   |
| SA ID numbers validated locally (date of birth + Luhn check digit) before any paid check; stored encrypted with a keyed hash for one-account-per-ID                                                                                                                                             | Saves failed paid lookups; no plain-text ID numbers                                                | Plain storage          |

## Additions in 4a-2 (buyer journey)

| Decision                                                                                                                                                                                                                           | Rationale                                                      | Alternative considered    |
| ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------- | ------------------------- |
| Verification in three independently saved steps (identity document, selfie, address and marital status) then one submit                                                                                                            | Buyers on phones can stop and continue later                   | One long form             |
| Identity data check runs through the routed provider on submit; the selfie and documents always go to the KYC review queue (4b)                                                                                                    | A data match alone doesn't prove the person holds the document | Auto-verify on data match |
| **Only staff decisions are final.** Automatic outcomes are recalculated from every check, so a passing ID check can never verify a buyer whose documents still need review (bug found in testing)                                  | Prevents premature verification                                | First result wins         |
| Selfie captured with the phone's front camera and reviewed by a person; the provider's hosted liveness widget (Sumsub WebSDK / Smile ID camera) is added once sandbox keys exist, with a CSP update for the provider's script host | Can't configure or test hosted liveness without keys           | Ship an untested widget   |
| Documents encrypted with the application key before writing to the private disk; read back only through the controller                                                                                                             | Encrypted at rest even if the disk is copied                   | Plain private files       |
| Spouse details encrypted in a text column (MySQL's JSON type rejects ciphertext; found in the MySQL run and fixed by a forward migration)                                                                                          | Correct on the production database                             | —                         |
| Married in community of property requires the spouse's name, a valid SA ID number and a signed consent document before submission                                                                                                  | Spouse consent rule from the PRD                               | Ask later                 |

## Additions in 4b-1 (KYC review, screening, refund account)

| Decision                                                                                                                                                                                                                   | Rationale                                                                       | Alternative considered |
| -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------- | ---------------------- |
| KYC review queue with tabs (needs review, bank accounts, screening due, verified, rejected); viewing needs `kyc.view`, approving `kyc.approve`, rejecting / asking for more `kyc.reject`                                   | Separation of duties between seeing and deciding                                | One permission         |
| Documents decrypted only by the review controller, served inline with `no-store` and `nosniff`; every opening audit-logged                                                                                                 | Who looked at whose ID is always known                                          | Signed file URLs       |
| Approval requires a **clear** sanctions/PEP screening recorded in the last 30 days; a possible or confirmed match needs written details and blocks approval                                                                | FICA screening before onboarding; matches resolved by a person                  | Approve, screen later  |
| Screening recorded by a KYC officer (result, lists checked, note) until provider AML endpoints are confirmed in sandbox; same record used by automatic screening later                                                     | Works on day one; no unconfirmed integration                                    | Wait for providers     |
| "Screening due" list: verified buyers not screened in 30 days (they cannot be approved for a listing until screened again, enforced in 4b-2)                                                                               | Ongoing monitoring                                                              | Screen once            |
| "Ask for more information" reopens the submission for the buyer and emails the request; the message is shown on their verification page                                                                                    | Fixes small problems without a rejection                                        | Reject and restart     |
| Refund account: holder must be the buyer, account number encrypted (last 4 shown), bank letter/statement required, re-checked whenever changed, and **locked** while a deposit or refund is pending (lock set by Sprint 5) | Refunds only to the bidder's own account; no last-minute redirection of refunds | Free changes           |
| Branch codes pre-filled from each bank's universal branch code but editable                                                                                                                                                | Fewer typing errors; Thabekhulu to confirm the list                             | Free text only         |

## Additions in 4b-2 (companies, proof of funds, bidder approval)

| Decision                                                                                                                                                                                                                                            | Rationale                                                                     | Alternative considered   |
| --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------- | ------------------------ |
| One `BidderEligibility` service produces the approval checklist for staff and buyers; approval is refused server-side unless every required item passes                                                                                             | One rule set; the UI can't be bypassed                                        | Checks in each screen    |
| Required: identity verified and in date, clear screening in 30 days, refund account verified, company/trust verified (if bidding for one), proof of funds accepted, in date (90 days) and covering the minimum (Mining and minimums ≥ R5m, setting) | K6 and the investor brief                                                     | Global approval          |
| Deposit received (Sprint 5) and data-room NDA (4c) appear on the checklist as "later" and don't block until their sprints add them                                                                                                                  | Honest about what isn't checked yet                                           | Hide them                |
| Approval is per listing; each approved bidder gets a random 4-digit number unique within that listing, shown publicly instead of names                                                                                                              | Bidders can't be linked across auctions; matches the approved bid-feed design | One global bidder number |
| The checklist is snapshotted at decision time; approvals can be withdrawn with a reason; rejected applicants may re-apply                                                                                                                           | Audit trail; correctable mistakes                                             | Live-only state          |
| Company (CIPC `YYYY/NNNNNN/NN`) and trust (Master's reference) bidders list everyone in control and owners of 25%+, encrypted; verified with `kyc.approve_company` (KYC officers by default)                                                        | Beneficial ownership under FICA                                               | Name only                |
| Proof of funds: the KYC officer records the amount actually shown on the document when accepting                                                                                                                                                    | The buyer's typed figure isn't trusted                                        | Use the typed amount     |
| Personal and company documents share one `SecureFiles` helper (encrypt before write, decrypt only in staff controllers, every opening audit-logged)                                                                                                 | One implementation to review                                                  | Per-feature code         |
